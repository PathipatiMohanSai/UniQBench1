# UniQBench — Locked Ten-Module Implementation Plan

## Project objective

UniQBench will be implemented as a reproducible benchmarking system for a fixed variational quantum classifier. The system will use one controlled data pipeline and one controlled model pipeline, then execute comparable experiments across selected backend conditions. Every numerical result, table, figure, and summary file will be generated by the ten project modules and traced to the raw experiment records they produce.

The initial implementation will prioritize a working, reproducible experiment over an oversized feature set. It will not claim quantum advantage, universal portability, publication, or any numerical result before the experiment runner produces it.

## Locked research question

> How do backend-specific execution and noise conditions affect the reproducibility, predictive performance, and computational cost of the same variational quantum classifier under a controlled experimental protocol?

## Locked ten-module architecture

| Module | File | Responsibility | Primary outputs |
|---:|---|---|---|
| 1 | `config.py` | Validated experiment configuration, seeds, paths, dataset/model/backend parameters | Immutable configuration object and run manifest |
| 2 | `data.py` | Dataset acquisition, validation, standardization, PCA, deterministic train/validation/test splits | Processed arrays, split manifest, PCA explained-variance record |
| 3 | `circuit.py` | Backend-neutral angle encoding, variational layers, entanglement pattern, measurement definition | Circuit specification and serialized circuit metadata |
| 4 | `model.py` | Hybrid VQC plus classical prediction head, loss, optimizer, initialization | Trainable model and parameter metadata |
| 5 | `backends.py` | Backend registry and execution adapters; simulator, noisy simulator, optional IBM hardware adapter | Backend capability and execution records |
| 6 | `training.py` | Deterministic training loop, validation, checkpointing, seed handling, metric logging | Per-epoch logs and trained checkpoints |
| 7 | `benchmark.py` | Experiment matrix orchestration; executes modules 1–6 and records every run | Raw run-level results in CSV/JSONL |
| 8 | `metrics.py` | Accuracy, macro-F1, loss, timing, circuit statistics, uncertainty, optional NPS | Metric tables and metric definitions |
| 9 | `analysis.py` | Aggregation, confidence intervals, backend comparisons, ablations, statistical summaries | Analysis tables and publication figures |
| 10 | `report.py` | Generate a reproducibility report, experiment manifest, results summary, and paper-ready tables | Markdown/CSV/PNG report package |

## Orchestration rule

A single thin command-line entry point may call the ten modules in order, but it will contain no scientific logic, no hidden constants, and no independently calculated results. All data processing, circuit generation, backend execution, metric calculation, analysis, and report generation must occur inside the ten locked modules.

## Initial experimental scope

The first complete run will use a two-class MNIST task or another explicitly documented public image dataset, PCA to four and eight components, four- and eight-qubit circuits, four circuit depths, at least three independent seeds, one reference simulator, and one additional backend condition. An optional IBM hardware run may be added only after the local pipeline passes validation. CIFAR-10, 16-qubit runs, GPU scaling, and additional platforms are extensions, not blockers for the first complete implementation.

## Reproducibility contract

Every run must record the code version, configuration hash, dataset hash, split seed, model seed, backend name, backend version, simulator or hardware status, shots, optimizer settings, circuit width, depth, training size, execution time boundaries, circuit statistics, and timestamp. Raw observations must never be overwritten. Aggregated tables and figures must be generated from raw run records.

## Result integrity rules

The implementation must not embed or reuse the transcript’s placeholder values of 34.7% divergence, 623× speedup, NPS above 0.82, 92% MNIST retention, or 45% CIFAR-10 retention. If the experiment does not measure a value, the report must display `not_measured`, not a guessed or placeholder number. Physical hardware results and simulated results must be stored and analyzed separately.

NPS, if enabled, will be reported as a secondary exploratory metric. The implementation must document its population, standard-deviation convention, zero-mean handling, and possible negative values. It must not label a threshold as a universal design rule without validation.

## Definition of completion

The project is complete when the ten modules can execute a clean run from a fresh environment, create raw run records, generate metric tables and figures from those records, and produce a report that another researcher can reproduce using the same configuration and seed manifest. A paper-ready result requires successful validation, repeated runs, baseline comparisons, uncertainty reporting, and a limitations section.
